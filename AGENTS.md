# Правила работы над проектом

## Цель и контекст

Создать небольшой 3D-платформер про хоббита, прыгающего по плывущим брёвнам и бочкам. Согласованный объём и этапы: `doc/initial-plan.md`. Порядок проверки: `doc/gauntlet-loop.md`. Текущее состояние: `doc/workbench.md`.

Общаться с пользователем и вести проектную документацию на русском. Имена файлов, узлов и программных сущностей делать понятными и последовательными; для кода использовать английские имена.

## Работа с проектом

- Перед реализацией проверить фактическую версию Godot и доступные средства запуска. Предварительная цель — Godot 4 и GDScript; не смешивать API разных основных версий.
- Сначала добиться работоспособности на простых фигурах. Модели и эффекты добавлять после проверки основной механики.
- Сохранять небольшой объём первой версии. Не добавлять новые игровые системы без основания в задаче пользователя.
- Выбирать простую структуру сцен и небольшие скрипты с ясной ответственностью. Не создавать архитектуру для предполагаемых будущих функций.
- Движение платформ должно быть предсказуемым. Отдельно проверять перенос героя, отрыв при прыжке и возврат после падения.
- Клавиатура и геймпад поддерживаются с первого прототипа через общие действия Input Map. Сохранять аналоговую скорость, мёртвую зону и управление меню без мыши. Синтетические события не заменяют проверку физического контроллера.
- Настраиваемые параметры движения и прыжка выносить в доступные редактору свойства, когда это помогает настройке игры.
- Не предполагать наличие MCP. Проверять доступность инструментов; при необходимости использовать файлы проекта, командную строку и скрипты Blender.
- Сохранять исходники создаваемых ресурсов и способ их воспроизведения. Не редактировать вручную кэш `.godot/`; сохранять нужные проекту файлы идентификаторов ресурсов.
- Не перезаписывать работу пользователя, не выполнять разрушительные Git-операции. Коммиты и публикацию делать по запросу пользователя.

## Gauntlet Loop и агенты

Для существенных игровых изменений применять цикл из `doc/gauntlet-loop.md`. Эти инструкции разрешают делегирование: выделять независимого критика в отдельного агента со свежим контекстом. Реализацию делегировать при наличии полезных независимых задач; для небольших правок документации делегирование необязательно.

Критику передавать цель, критерии, применимые правила и реальные артефакты. Автор изменения не может единолично объявить независимую проверку пройденной. Критик не должен редактировать проверяемые файлы во время ревью. При параллельной реализации явно разделять владельцев файлов и интегрировать результат перед общей проверкой.

Исправлять замечания, влияющие на согласованные критерии, и повторять проверку до их выполнения. Не расширять бесконечно объём работы: идеи сверх текущей цели записывать отдельно. При недоступности инструментов фиксировать ограничение и продолжать доступную часть задачи.

## Проверка и отчётность

- Проверять результат соразмерно изменению. Для документации достаточно проверить содержимое, ссылки и diff; не создавать формальные тесты ради тестов.
- Для игровых изменений использовать проверку импорта/запуска и игровые сценарии из документа Gauntlet Loop. Проверка без окна не доказывает качество управления, камеры или графики.
- Точные команды проверок записывать после обнаружения редакторов. Не выдавать предполагаемые команды за выполненные.
- Сохранять доказательства: результаты команд, при необходимости кадры или запись прохождения. Не утверждать, что игра протестирована, если запуск не состоялся.
- Обновлять `doc/workbench.md` после существенного этапа или проверки. Различать реализованное, проверенное и ожидающее проверки.
- В итоговом сообщении кратко указывать изменения, фактические проверки и оставшиеся ограничения.
